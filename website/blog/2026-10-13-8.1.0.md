Babel 8.1.0 is out!

This is the first minor release since [Babel 8.0.0](./2026-06-16-8.0.0.md). It includes transform support for the [Import Bytes](https://github.com/tc39/proposal-import-bytes) and [Import Text](https://github.com/tc39/proposal-import-text) proposals, and experimental support for generating source maps with [range mappings](https://github.com/tc39/ecma426/blob/main/proposals/range-mappings.md). `@babel/parser` now supports multiple new TC39 proposals: [deferred re-exports](https://github.com/tc39/proposal-deferred-reexports), [`import.sync`](https://github.com/tc39/proposal-import-sync), [structs](https://github.com/tc39/proposal-structs), and the latest version of [partial application](https://github.com/tc39/proposal-partial-application).

We also added `recommended` and `all` configs to `@babel/eslint-plugin`, for parity with ESLint's built-in presets.

You can read the whole changelog [on GitHub](https://github.com/babel/babel/releases/tag/v8.1.0).

## Highlights

### Import bytes and text ([#17817](https://github.com/babel/babel/pull/17817))

The [Import Bytes](https://github.com/tc39/proposal-import-bytes) (Stage 2.7) and [Import Text](https://github.com/tc39/proposal-import-text) (Stage 3) proposals build on top of [import attributes](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/with), similarly to [JSON modules](./2024-02-28-7.24.0.md#json-modules-imports-15829-15870). They allow importing any file either as raw bytes, or as a string:

```js title="input.mjs"
import logo from "./logo.png" with { type: "bytes" };
import shader from "./shader.glsl" with { type: "text" };

logo; // An Uint8Array, backed by an immutable ArrayBuffer when supported
shader; // A string
```

Like [`@babel/plugin-transform-json-modules`](https://babeljs.io/docs/babel-plugin-transform-json-modules), the new [`@babel/plugin-proposal-bytes-modules`](TODO: link to docs) and [`@babel/plugin-proposal-text-modules`](TODO: link to docs) plugins transform these imports to the appropriate way of loading files in your target platform(s), according to your [`targets`](https://babeljs.io/docs/options#targets) option. For example, when targeting browsers Babel compiles `import logo from "./logo.png" with { type: "bytes" }` to:

```js
const logo = await fetch(import.meta.resolve("./logo.png"))
  .then(r => r.bytes())
  .then(_immutableUint8Array);
```

while when compiling to CommonJS for Node.js it will generate:

```js
const logo = _immutableUint8Array(
  require("fs").readFileSync(require.resolve("./logo.png"))
);
```

You can enable them by adding the plugins to your Babel config:

```jsonc title="babel.config.json"
{
  "targets": ["chrome 120", "firefox 120", "node 22"],
  "plugins": [
    "@babel/plugin-proposal-bytes-modules",
    "@babel/plugin-proposal-text-modules"
  ]
}
```

### Source map range mappings ([#18006](https://github.com/babel/babel/pull/18006))

Source maps have recently started evolving again, under TC39's TG4 group. The [range mappings](https://github.com/tc39/ecma426/blob/main/proposals/range-mappings.md) Stage 3 proposal is one of the new additions, and aims at increasing source map quality while reducing their size.

Source maps encode a list of _points_: each mapping says that a given position in the generated code corresponds to a given position in the original code. Any character that is not mapped by a specific source map location is assumed to map to the same point that the _previous_ mapping was pointing to: tools that generate JavaScript thus have to emit a lot of mappings, even for lightly modified code. This makes source maps large.

Range mappings allow marking some mappings as covering a whole _range_ of code, allowing representing multiple point-to-point mapping as if they were a single one.

For example, given this input where a plugin renames `z` to `a`:

```js
let x, y, z, w;
x + y + z +   w;
```

Babel would usually generate the following `mappings`:

```
AAAA,IAAI,CAAC,EAAE,CAAC,EAAEA,CAAC,EAAE,CAAC;AACd,CAAC,GAAG,CAAC,GAAGA,CAAC,GAAK,CAAC
```

while with range mappings it generates:

```
AAAA,QAAQ,EAAEA,CAAC;KACN,GAAGA,CAAC,GAAK,CAAC
```

together with an additional `"rangeMappings": "AD;D"` field.

You can enable range mappings using the new [`sourceMapRanges`](TODO: link to docs) generator option:

```jsonc title="babel.config.json"
{
  "sourceMaps": true,
  "generatorOpts": {
    "sourceMapRanges": true
  }
}
```

:::caution
Only enable this option if all the tools that run after Babel and consume its source maps, including your browser's devtools, support range mappings. The option is currently ignored when also using `inputSourceMap`.
:::

### Parsing support for lots of new proposals

This Babel release also include _parsing_ support for multiple new proposals. Note that (except for [partial application](#partial-application-17785)) it doesn't support _transforming_ them yet: you can start playing around with them if you have other tools, such as bundlers, that can handle the new syntax.

#### Deferred re-exports ([#17617](https://github.com/babel/babel/pull/17617))

The [deferred re-exports](https://github.com/tc39/proposal-deferred-reexports) Stage 2.7 proposal extends [`import defer`](./2023-09-25-7.23.0.md#deferred-import-evaluation-15845-15878) to `export ... from` declarations. When a module re-exports bindings using `export defer`, the re-exported module is only loaded and evaluated if one of its bindings is actually imported:

```js title="my-library/index.js"
export defer { parse } from "./parser.js";
export defer { format } from "./formatter.js";
```

```js title="main.js"
// ./formatter.js will never be loaded nor executed
import { parse } from "my-library";
```

You can enable it using the `deferredReexports` parser plugin, together with `deferredImportEvaluation`.

#### Filtered namespace imports ([#17617](https://github.com/babel/babel/pull/17617))

The deferred re-exports proposal also introduces a new syntax to create namespace objects that only contain some of the exports of a module, which lets bundlers safely remove the unused ones:

```js
import { parse, format } as myLib from "my-library";
```

You can enable it using the `namespaceImportFilter` parser plugin.

#### `import.sync` ([#17980](https://github.com/babel/babel/pull/17980))

The [`import.sync`](https://github.com/tc39/proposal-import-sync) Stage 2 proposal allows loading and evaluating a module synchronously, when the runtime that the code runs in is able to do so:

```js
const { readFile } = import.sync("node:fs");
```

You can enable it using the `importSync` parser plugin.

#### Structs ([#17624](https://github.com/babel/babel/pull/17624))

The [structs](https://github.com/tc39/proposal-structs) Stage 2 proposal introduces a new kind of class-like declaration, whose instances have a fixed layout: all their fields are defined when they are created, and they cannot be extended with new properties:

```js
struct Point {
  x = 0;
  y = 0;

  get length() {
    return Math.hypot(this.x, this.y);
  }
}
```

You can enable it using the `structs` parser plugin. Babel only supports _non-shared_ structs, and not `shared struct` declarations.

#### Partial application ([#17785](https://github.com/babel/babel/pull/17785))

A few years ago the [partial application](https://github.com/tc39/proposal-partial-application) Stage 1 proposal introduced a new syntax, using `~(` to mark a partial call:

```js
const addOne = add~(1, ?);
addOne(2); // add(1, 2)

const log = console.log~("[LOG]", ...);
log("Hello", "world"); // console.log("[LOG]", "Hello", "world")
```

You can enable it using the `partialApplication` parser plugin with the `version: "2021-10"` option, or by passing `version: "2021-10"` to [`@babel/plugin-proposal-partial-application`](TODO: link to docs).

### `@babel/eslint-plugin` configs ([#17956](https://github.com/babel/babel/pull/17956), [#18009](https://github.com/babel/babel/pull/18009))

[`@babel/eslint-plugin`](https://babeljs.io/docs/babel-eslint-plugin) provides versions of some ESLint core rules that are compatible with experimental syntax supported by Babel. It now exposes two [configs](TODO: link to docs), `configs.recommended` and `configs.all`, which are meant to be used with the corresponding configs from `@eslint/js`.

They replace some of ESLint's rules with the equivalent Babel ones so that they work with new syntax, and they enable some new Babel-specific rules that would likely be in those ESLint presets if the syntax that they lint was already part of standard JavaScript.

```js title="eslint.config.js"
import js from "@eslint/js";
import babelParser from "@babel/eslint-parser";
import babelPlugin from "@babel/eslint-plugin";

export default [
  js.configs.recommended,
  {
    plugins: { babel: babelPlugin },
    languageOptions: { parser: babelParser },
    ...babelPlugin.configs.recommended,
  },
];
```

Note that the configs do not register the plugin and the parser for you: you still need to list it them in `plugins` and `languageOptions.parser`.
